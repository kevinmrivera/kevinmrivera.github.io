GoDaddy → Cloudflare DNS Migration

Move authoritative DNS to Cloudflare, preserve service continuity (web, email, SaaS), and enable Cloudflare SSL/WAF.

Runbook DNS Cutover

Preparation

  • Lower TTL on key records (A/CNAME/MX) to ~300–600 seconds at least a few hours before cutover.
  • Screenshot / export all DNS records (zone snapshot). Keep a rollback reference.
  • Identify records that typically stay DNS only: MX, SPF/DKIM/DMARC, autodiscover, sip, etc.
  • Confirm what hosts the website (e.g., Webflow/Netlify/WordPress) and how it expects DNS to be set.
  • Check if DNSSEC is enabled at GoDaddy (you’ll need to disable it before changing nameservers).
  • List “special” DNS records that should not be proxied: mail, verification TXT, DKIM selectors, MTA-STS, etc.

Migration Steps

  1. Add the domain to Cloudflare and choose a plan.
  2. Use Cloudflare to import/copy DNS records.
  3. Verify: all records copied over except NS records (NS is controlled by the registrar after cutover).
  4. Set correct proxy status:
    • Proxied: web records (usually www and/or root if allowed)
    • DNS only: MX/TXT/mail-related records and many SaaS verifications
  5. At GoDaddy: update nameservers to Cloudflare nameservers.
  6. Wait for nameserver propagation (can be quick, can take some time depending on caching).

Issues That May Arise

  • Error 1000 / Prohibited IP: Cloudflare proxying to an IP that Cloudflare blocks (common when origin is another Cloudflare / restricted range).
  • Webflow SSL nuance: Webflow expects www CNAME to their host; root may be A records or CNAME flattening depending on setup.
  • Wrong proxy setting on mail records can break email delivery.
  • DNSSEC mismatch can cause resolution failures after nameserver change.
  • Split hosting: multiple A records (load balancing) or mixed providers need careful parity.
  • Verification failures: Google/Microsoft/Salesforce DKIM TXT/CNAME entries must match exactly.

Post-Migration Validation

  • Confirm site loads for:
    • https://domain.com
    • https://www.domain.com
    • Any app subdomains (e.g., start, portal, mail)
  • Verify email: MX resolves correctly; SPF/DKIM/DMARC present; send/receive test.
  • Cloudflare SSL/TLS:
    • Set SSL mode to Full (Strict) if origin cert is valid (recommended).
    • Use Cloudflare Universal SSL for edge coverage (free).
  • Security / performance quick checks: caching off/on as needed, WAF rules baseline, redirects, HSTS (only after stable).
  • Rollback plan: keep GoDaddy DNS snapshot; if needed, revert nameservers back to GoDaddy temporarily.
Extra checklist (often missed)
  • Ensure there are no duplicate/conflicting records for the same host (e.g., www A + CNAME).
  • If using root CNAME flattening, confirm Cloudflare is set to allow it (it does).
  • Confirm any ACM/CAA records if you have them (certificate authority restrictions).
  • Confirm any _acme-challenge TXT records if using Let’s Encrypt validation elsewhere.
  • Don’t proxy: autodiscover, _sip, _sips, enterpriseenrollment unless you know the service supports proxying.

Microsoft 365 ↔ Google Workspace Calendar Interop (Free/Busy)

Enable cross-platform free/busy visibility between Exchange Online and Google Calendar using Calendar Interop.

Runbook Calendar

Preparation

  • Confirm which tenants/domains are participating and identify the interop alias domain strategy (if used).
  • Verify both environments are healthy:
    • Google Workspace domain + Calendar services operational
    • Exchange Online / Microsoft 365 mailboxes operational
  • Gather requirements + reference:
    • Google Admin: Calendar interop reference
  • Decide scope: free/busy only vs richer cross-scheduling capabilities.
  • Create test accounts in both platforms for validation (non-admin if possible).

Implementation Steps

  1. Configure Google Calendar Interop settings in Google Admin (Exchange environment details, routing, etc.).
  2. Configure Exchange Online side (availability / federation / org relationship as required by your chosen interop method).
  3. Ensure DNS dependencies are correct (as required):
    • Autodiscover and Exchange endpoints reachable
    • Any required validation TXT/CNAME records
  4. Confirm firewall/proxy rules allow required outbound/inbound connectivity (if restricted).
  5. Document final configuration, endpoints, and troubleshooting steps.

Issues That May Arise

  • Free/busy works in one direction but not the other (common: routing/auth mismatch).
  • Domain/alias mismatch between what users type and what the interop expects.
  • Calendar permission defaults too restrictive to expose free/busy.
  • Autodiscover or Exchange availability endpoint not reachable externally (DNS/proxy restrictions).
  • Cached results: it may take time for changes to fully apply.

Post-Implementation Validation

  • Use test accounts to validate free/busy in both directions:
    • Google user invites Microsoft user → can see free/busy
    • Microsoft user invites Google user → can see free/busy
  • Validate multiple scenarios:
    • Same domain vs alias domain (if used)
    • Internal vs external scheduling behaviors
    • Mobile vs desktop clients (Outlook, OWA, Google Calendar)
  • Record outcomes + troubleshooting notes (what fixed what).
Extra checklist (often missed)
  • Confirm calendar sharing defaults allow free/busy visibility where intended.
  • Ensure “external sharing” settings aren’t blocking the organization relationship.
  • Keep an interop “known-good” test meeting for quick regression testing later.
  • Document how users should search addresses (primary vs alias format).
